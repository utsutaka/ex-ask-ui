# 文章版の書式(質問と議論)

文章版は、ask-ui の書式(項目と順序)を、チャットの文章で表したもの。ブラウザでないと表示できない図表がつかない質問と議論の、通常の出し方であり、ask-ui の画面が技術的に使えないときの切り替え先でもある。使う場面と手順は、`SKILL.md` の「出し方の選び方」と「失敗時の切り替え」を参照する。

## 通知の有無

下の見本の先頭の通知(「ask-ui を使えないため、文章版で…します。(理由)」)は、**技術的な失敗で切り替えたときだけ**付ける。通常の出し方(失敗がなく、画面が要る図表がつかないとき)では、通知を付けず、見本の 2 行目以降(質問は「## 問 1: …」、議論は「## <論点の名前>」)から書き始める。項目、順序、回答の形、依頼文で終えること、機能 005 の規則は、どちらも同じ。

## 質問の見本

質問は、1〜4 問を 1 回に出す。項目の名前と順序は、ask-ui の画面と同じ。各項目に含める要素は、`SKILL.md` の「質問の規則」と「文章にする章の書き方」と同じ。

````markdown
ask-ui を使えないため、文章版で質問します。(chrome-devtools のツールが使えません)

## 問 1: 設定ファイルの形式は、どれにしますか?

### 決めること
設定ファイルの形式を決めてください。以降の作業が、この形式を前提に進むため、先に決めておく必要があります。回答がないと次に進めないので必須で、今日中に決めたい事項です。利用者の指示がきっかけで、根拠は確実です。

### 1. 現状
設定は今、3 つのファイルに分かれていて、読み込みの処理もファイルごとに別々です。決定済みなのは、設定を 1 つにまとめる方針だけで、spec.md の「設定」の節に書いてあります。形式は、まだ決まっていません。

### 2. 問題点
利用者が、設定の値を直したいとき、3 つのファイルのどれに書くのかが分からず、探すところから始まります。たとえば、直したつもりが、別のファイルの値に上書きされていて、動作が変わらないまま、時間を使います。形式を決めずに進めると、設定が増えるたびに、同じことが起きます。

| 項目 | 案 A | 案 B |
| --- | --- | --- |
| 導入 | 不要 | 必要 |

```text
今:    設定 1 -> 読み込み 1
       設定 2 -> 読み込み 2      (ファイルごとに別々)
       設定 3 -> 読み込み 3
案 A:  設定 1 + 設定 2 + 設定 3 -> 1 つのファイル -> 読み込み(1 か所)
```

### 3. あるべき姿
設定の値の置き場所が 1 か所に決まり、直したい値がどこにあるかを、探さずに分かる状態です。判断の基準は 2 つです。(1) 値を書く場所が、1 つに決まる。(2) 直した値が、そのまま動作に反映される。

### 4. 推奨
推奨案：案 A

案 A を推奨します。あるべき姿に最も近く、導入の手間も最小のためです。採用すると、3 つの設定ファイルを 1 つにまとめ、読み込みの処理を 1 か所に集約します。

### 5. 選択肢
1. 案 A(推奨)
    - 内容: 案 Aの内容
    - 効果: 案 Aの効果
    - リスク: 特筆するリスクはありません
    - あるべき姿との一致: 高(あるべき姿に最も近い)
2. 案 B
    - 内容: 案 Bの内容
    - 効果: 案 Bの効果
    - リスク: 戻せない可能性：未コミットの設定ファイルを上書きします
    - あるべき姿との一致: 中(理由を書きます)
    - 推奨との違い: 案 A より、導入が重い

選択肢の番号で答えてください(複数問のときは「問 1: 2、問 2: 1, 3」の形。自由記入も受けます)。
````

- 複数問のときは、`## 問 2: …` のように、問を続ける。最後の依頼文は、全問の後に 1 回だけ置く
- 推奨を示せないときは、「推奨案：なし」と書き、示せない理由と、判断に必要な情報を書く。このとき、どの選択肢にも「(推奨)」と「推奨との違い」を付けない
- 複数選択の問は、「複数選べます」と添える

## 議論の見本

議論は、選ばずに、自由に返信してもらう。項目の名前と順序は、ask-ui の画面と同じ。

````markdown
ask-ui を使えないため、文章版で議論します。(chrome-devtools のツールが使えません)

## 設定ファイルの管理方針

### 議論したいこと
問い:
1. 設定は、1 つにまとめるべきか
2. 環境ごとの違いは、どこに置くか

設定の管理方針は、以降の作業の前提になるため、先に議論しておく価値があります。決めなくても作業は進められますが、早いほど手戻りが少なくなります。利用者の発言がきっかけで、根拠は確実です。

### 1. 現状
今の設定は、3 つのファイルに分かれています。決定済みの事項は、まだありません。

### 2. 問題点
利用者が、設定の値を直したいとき、3 つのファイルのどれに書くのかが分からず、探すところから始まります。たとえば、直したつもりが、別のファイルの値に上書きされていて、動作が変わらないまま、時間を使います。管理の方針を決めずに進めると、設定が増えるたびに、同じことが起きます。

### 3. あるべき姿
設定の値の置き場所が 1 か所に決まり、直したい値がどこにあるかを、探さずに分かる状態です。判断の基準は 2 つです。(1) 値を書く場所が、1 つに決まる。(2) 直した値が、そのまま動作に反映される。

### 4. 叩き台
| 項目 | 叩き台 X | 叩き台 Y |
| --- | --- | --- |
| 内容 | 叩き台 Xの内容 | 叩き台 Yの内容 |
| 効果 | 叩き台 Xの効果 | 叩き台 Yの効果 |
| リスク | 叩き台 Xのリスク | 叩き台 Yのリスク |
| あるべき姿との一致 | 中(理由を書きます) | 中(理由を書きます) |
| まだ決まっていない点 | 叩き台 Xで、まだ決まっていない点 | 叩き台 Yで、まだ決まっていない点 |

### 5. 見立て
仮の結論(選ばせるための推奨ではなく、議論の出発点): 叩き台 X を軸にするのがよさそうです

根拠: あるべき姿との一致が高いため

まだ分からないこと: 運用コストの実測がありません

確信の度合い: 中(根拠に、推測を含むため)

### 6. ご意見
賛成できる点、引っかかる点、足りない視点を書いてください。

ご意見をください(賛成できる点、引っかかる点、足りない視点を、自由に書いてください)。
````

- 叩き台は 2〜4 件。比較できる表を添える
- 見立ては、選ばせるための推奨ではなく、議論の出発点であることを書く

## 回答の形

| 書式 | 答え方 | 例 |
| --- | --- | --- |
| 質問(1 問) | 選択肢の番号。複数選択は、番号をコンマで並べる。自由記入は、文章で | `2`、`1, 3` |
| 質問(複数問) | 「問 N: 番号」を、コンマか読点で並べる | `問 1: 2、問 2: 1, 3` |
| 議論 | 自由な返信 | - |

表記の揺れ(「問1は2」など)は、受け取る側が解釈する。曖昧なときは、依頼文で確認する(疑問文で終えない)。

## 図表の置き換え

文章版では、図表を、チャットの文章で表せる形に置き換える。

| ask-ui の図表 | 文章版 |
| --- | --- |
| 表(table) | Markdown の表 |
| 流れ図、構造図、タイミングチャートなどの SVG | 罫線と矢印の文字の図(`text` のコードの囲み)。棒グラフは、文字の棒(`█`)と数値 |
| mermaid | 使わない。内容を、表か文字の図で書き直す(読めない人がいるため) |
| 画面デザインのモック、配色の見本、細かい SVG | 出さない。下の定型を書く |

出さなかったときの定型: `(図表「<題名>」は、文章では表せないため、出していません。内容: <一言の説明>)`

## 書き方の規則

- 最後の行は、依頼文(「番号で答えてください」「ご意見をください」など)で終える。疑問文(`?`、「〜ですか」「〜でしょうか」など)で終えない。Stop フックは、最後の行が質問の形のときに差し戻すため
- 機能 005 の共通規則に従う(`SKILL.md` の「文章の書き方(共通)」。縮めた語は初出で定義し、前提知識は一言添える。題名と結論や要点の箇所は、略称を使わない)
- 利用者への呼びかけは、`SKILL.md` の「利用者の呼び方(共通)」に従う(プロジェクトの指示に呼称の定義があればそれに従い、なければ主語を省く。「あなた」は使わない)
- 文章版にも、機密情報(ID、パスワード、API Key、`.env` の内容など)を書かない。票がなく、検証の対象外のため
- 1 回に出せるのは、1〜4 件。質問と議論は、混ぜない
- 保存の対象外。文章版には、「この質問を保存する」がない
