# ask-ui: 図表つきの質問と議論にブラウザで答えてもらう

利用者への質問は、すべてこのスキルで表示する(文字だけで足りる質問も同じ)。1 回に 1〜4 件を表示する。質問は、案(選択肢)を選んで答える。議論は、案を選ばず、自由記入で意見を返してもらう。表、簡単な図、画面デザインのモックも添えられる。

## 使い分け

- 利用者に質問する場面は、図表の有無によらず、すべてこのスキルを使う
- 1 つに決めてほしいときは**質問**、論点を深めたい(結論を急がない)ときは**議論**を使う。推奨を示せないときも、選んでほしいなら質問で、「推奨案：なし」と書く
- 1 回の表示は、質問だけ、または議論だけ(混在させない)
- `AskUserQuestion` は、このスキルが技術的に失敗したときだけ使う(下の「失敗時の切り替え」)。返答が質問で終わると、フックが差し戻し、このスキルを使うよう伝える。文章で質問しない
- ツールの実行の許可を尋ねる権限の確認は、質問に含めない(この仕組みの対象外)
- 調査の報告と、UI を使った説明は、質問ではない。回答を求めず、`AskUserQuestion` へは切り替えない(下の「報告・説明の手順」)
- chrome-devtools MCP は、窓つき(`--headless` なし)で動いている必要がある

## 全体の流れ

1. 作業フォルダ `<作業フォルダ>` を作り、その絶対パスを控える(場所の決め方は、下の「作業フォルダの決め方」)。以降の手順の `<作業フォルダ>` は、すべてこのパス
2. 票 `questions.json` を書く(質問も議論も、ルートは `kind` と `items`。形は `references/board-examples.md` の例と、下の「質問の規則」「議論の規則」を参照)
3. 必要なら文章を推敲する(下の「推敲」を参照)
4. 票を検証する
5. 管理用ページのローダーを生成する
6. ブラウザに表示する
7. 回答または中断の目印が出るまで待つ
8. 結果を取り出す。`save` が真なら、保存する(下の「保存」)
9. ページを閉じ、作業フォルダを削除する

`<スキルのフォルダ>` は `${CLAUDE_SKILL_DIR}` で参照する。ユーザー名や固定のパスは書かない。

## 作業フォルダの決め方

票や生成物を置く一時のフォルダ(`<作業フォルダ>`)は、次の順で、最初に使えるものを選ぶ。書き込みに失敗したときは、次の候補に進む。プロジェクトの中に、場所を決め打ちにしない。

1. プロジェクトの規則(`CLAUDE.md` など)に、一時ファイルの場所の指定があれば、それに従う(例: プロジェクト内の、指定されたフォルダの下の `<作業名>/`)
2. Claude Code の scratchpad。システムプロンプトに「Scratchpad directory」としてパスが示されているときは、その下に `ask-ui-<日時>/` を作る(プロジェクトの中を汚さず、権限の確認も出ない)
3. OS の temp フォルダ(1 と 2 が使えないとき)。次のコマンドが出力するフォルダを使う(名前に乱数が付き、ほかの利用者のフォルダと重ならない)

```bash
node -e "console.log(require('fs').mkdtempSync(require('path').join(require('os').tmpdir(), 'ask-ui-')))"
```


- 作ったフォルダの絶対パスを控え、以降のすべての手順で使う(`evaluate_script` の `sourcePath` も、この絶対パス)
- 使い終わったら、必ず削除する(下の「後片付け」)。ほかの人のファイルは、消さない

票のルートの `kind`(`question` または `discussion`)は、`build-pages.mjs` の引数 `--kind report|explain`(報告・説明の種別)とは別のものである。票の `kind` は、ファイルの中の項目で、引数ではない。

## 質問の規則

票は、次の規則を満たす必要がある。満たさない票は、検証で拒否され、画面に出ない。古い形式(ルートが `questions`、項目が `history`、`background` など)の票も拒否される。

- `kind`: `question`。`items`: 1〜4 問
- 質問ごとに、次の項目が必要(画面には、この順に、上から並べて表示される)

| 画面の見出し | 項目 | 書くこと |
| --- | --- | --- |
| (題名) | `title` | 完全な疑問文。何を決める質問かが、題名だけで分かる(形は、検証では確かめない) |
| 決めること | `decide` | `text`(1 つの自然な文章。何を決めるか、意義と狙い、重要度、きっかけを含める。下の「文章にする章の書き方」) |
| 1. 現状 | `current` | `text`(1 つの自然な文章。概要と、決定済みの事項と反映先を含める)、`original`(原文。ある場合だけ。逐語の引用で、引用の見た目で表示される) |
| 2. 問題点 | `problem` | `description`(現状の問題、または引き起こす問題)、`exhibits`(図表。下の「図表の選び方」)。図表を付けない場合は、`noExhibitReason` に、要らない理由を書く |
| 3. あるべき姿 | `ideal` | `vision`(成果物の利用者が喜ぶ姿)、`notes`(採用するときの注意事項。ある場合だけ)。答えてほしい観点も、ここに含める |
| 4. 推奨 | `recommendation` | `given`(`text` = 最適である理由と、修正イメージを含む 1 つの文章)、または `none`(`text` = 示せない理由と、判断に必要な情報を含む 1 つの文章)のどちらか 1 つ。「推奨案：」の行は、先頭の選択肢の名前(なしのときは「なし」)が自動で表示される |
| 5. あなたの選択 | `options`、`multiple`、`allowFreeText` | 下の「選択肢の規則」 |

- `id`(英数字とハイフン)は、票と項目の中で、重複しない
- `allowFreeText` は、常に true
- 各項目の文は、段落ごとに改行して書いてよい(画面でも、改行どおりに表示される)
- 旧項目(`content`、`significance`、`importance`、`source`、`summary`、`decided`、`reason`、`image`、`info`)を渡すと、検証が拒否し、新しい欄(`text`)を案内する

### 文章にする章の書き方

「決めること」「1. 現状」「4. 推奨」(議論は「議論したいこと」)は、項目名をつけず、**1 つの自然な文章**として表示される。項目ごとに分けて書かず、次の要素を、文章の中に含める。要素は、検証では確かめられないため、書き落とさないよう、ここで確認する。

| 章 | 欄 | 文章に含める要素 | 長さの目安 |
| --- | --- | --- | --- |
| 決めること | `decide.text` | 何を決めるか / なぜ決める必要があるか(意義と狙い) / 重要度(必須か任意か。根拠と期限。思いつきの提案なら、そう書く) / きっかけ(出所と、根拠の確かさ) | 3〜5 文 |
| 1. 現状 | `current.text` | 今の状況の概要 / 決定済みの事項と、その反映先(どの文書の、どこ。なければ「決定済みの事項はまだない」) / まだ決まっていないこと | 3〜5 文 |
| 4. 推奨(あり) | `recommendation.given.text` | 推奨する理由 / 採用すると、何をどう変えるか(修正イメージ。具体的に) | 2〜4 文 |
| 4. 推奨(なし) | `recommendation.none.text` | 推奨を示せない理由 / 判断に必要な情報 | 2〜3 文 |
| 議論したいこと | `topic.text` | 意義と狙い / 重要度 / きっかけ(論点の問いは `questions`) | 3〜4 文 |

書き方の規則:

- 要素を、つなげただけにしない。「内容は〜。意義は〜。重要度は〜。」のように、項目名を読み上げる文にしない。前の文を受けて次の文が続くように書く
- 同じ内容を、言い換えて繰り返さない。1 つの要素は、1 回だけ書く
- 数字、文書名、節、コミットなど、確かめられる具体を入れる(「いくつか」「以前」と書かない)
- 句点で終わる文で書く。長くなる場合は、段落を分けてよい(改行どおりに表示される)
- 「推奨案：」の行は自動で出るため、案の名前を `text` の冒頭で繰り返さない。ただし、理由で案に触れるのは構わない

良い例(決めること):

> Stop フックを正式に採用するとき、観察用の記録をどうするかを決めてください。記録処理が配布物の ZIP に入っていて、利用者のプロジェクトに返答の一部が残るため、次に配布物を渡す前に決める必要があります。必須ですが急ぎではありません。specs/001 の T061(未完了)がきっかけで、根拠は確実です。

悪い例(項目名の読み上げ):

> 内容は、観察用の記録の扱いを決めることです。意義と狙いは、利用者の環境に記録が残ることです。重要度は必須です。出所は T061 です。

良い例(1. 現状):

> Stop フックは、返答の最後が質問の形のとき、差し戻して ask-ui で質問し直させます。2026-10-26 から、判定の結果を stop-hook.log に記録していて、432 件のうち 39 件は試験の入力でした。決定済みなのは、フックを採用する方針だけで、憲法 v2.0.0 と specs/001 の spec.md に書いてあります。記録の扱いは、まだ決まっていません。

悪い例(要素の書き落とし。決定済みの事項と反映先がない):

> Stop フックは、質問で終わる返答を差し戻します。観察用の記録があります。

良い例(4. 推奨、あり):

> 案 A を推奨します。利用者の環境に記録が残らなくなり、精度を測るときだけ記録も取れるためです。採用すると、recordObservation を環境変数のときだけ動くようにし、既定では何も書かないように変えます。

悪い例(修正イメージが具体的でない):

> 案 A が最適です。記録を適切に扱うようにします。

### 選択肢の規則

- `options`: 2〜4 件。選択肢ごとに、`id`、`label`(案の名前)、`recommended`、`content`(内容)、`effect`(効果)、`feasibility`(実現の可否)、`risk`(リスク・デメリット)、`fit`(あるべき姿との一致)が必要
- `fit` は、`level`(`高`、`中`、`低` のいずれか)と、`reason`(理由)
- 推奨あり(`recommendation.given`): 先頭の選択肢だけ `recommended: true`。先頭は `differenceFromRecommended`(推奨との違い)を持たず、先頭以外は持つ。複数選択の質問でも、推奨は先頭の 1 件(組み合わせを推奨したいときは、`given.text` に書く)
- 推奨なし(`recommendation.none`): すべて `recommended: false` で、どの選択肢も `differenceFromRecommended` を持たない。画面には「推奨案：なし」と示される
- **戻せない可能性：** ファイルやデータの削除、データの書き換え、外部への送信や公開、未コミットの変更の上書きのときだけ、`risk` の先頭に「戻せない可能性：」と書き、何が戻せないかを 1 行で示す。通常の文書や設定の変更では書かない(戻せるかどうかは、利用者の環境に任せる)
- `effect`(案を実行して得られる結果)と `fit`(あるべき姿への近さ)は、同じことを重複して書かない

## 議論の規則

議論は、質問と同じ画面の部品を使い、項目の組み合わせと回答欄だけが違う。選んで答えず、自由記入だけで答える(自由記入は必須)。

- `kind`: `discussion`。`items`: 1〜4 件
- 議論ごとに、次の項目が必要(`options`、`multiple`、`recommendation`、`allowFreeText` は持たない)

| 画面の見出し | 項目 | 書くこと |
| --- | --- | --- |
| (題名) | `title` | 論点の名前(疑問文にしない) |
| 議論したいこと | `topic` | `questions`(論点の問い。1〜3 件)、`text`(意義と狙い、重要度、きっかけを含む 1 つの文章) |
| 1. 現状、2. 問題点、3. あるべき姿 | `current`、`problem`、`ideal` | 質問と同じ |
| 4. 叩き台 | `drafts` | 2〜4 件。選ばず、比べる。`id`、`label`、`content`、`effect`、`risk`、`fit`、`open`(未解決の点) |
| 5. 見立て | `view` | `conclusion`(仮の結論。選ばせるための推奨ではなく、議論の出発点)、`basis`(根拠)、`unknown`(まだ分からないこと)、`confidence`(確信の度合い。`fit` と同じ `level` と `reason`) |
| 6. ご意見 | `opinion` | `guide`(書いてほしい観点)。回答は、この下の自由記入欄 |


### 図表の選び方

文字だけで説明せず、内容に合う図表を付ける。見本は、`references/exhibit-examples.md` にある(必要なときに読む)。

| 伝えたいこと | 使うもの | `kind` |
| --- | --- | --- |
| 項目を比べる(作業量、メリット、デメリットなど) | 表 | `table` |
| 手順、処理の流れ | 流れ図。mermaid の記述で書く(`graph`) | `mermaid` |
| 状態の移り変わり | 状態の図。mermaid(`stateDiagram-v2`) | `mermaid` |
| 順序、やり取り(誰が誰に何を送るか) | シーケンス図。mermaid(`sequenceDiagram`) | `mermaid` |
| 部品の関係、何が何を持つか、データの関係 | クラス図、ER 図。mermaid(`classDiagram`、`erDiagram`) | `mermaid` |
| 量の比較 | 棒グラフ。mermaid(`xychart-beta`)か、SVG | `mermaid`、`svg` |
| 時間の長さを軸に、いつ何が動くか。細かい配置が要る図 | タイミングチャート、構造図(SVG) | `svg` |
| 画面、見た目 | 画面案(モック)。案を比べるときは、並べて見せる | `mock` |

- `mermaid`: `source` に、mermaid の記述を書く(`html` は持たない)。5,000 文字まで。対応する図は、フローチャート、状態、シーケンス、クラス、ER、XY の 6 種(ガント、円グラフ、マインドマップなどは、対応していない)。日本語だけの subgraph 名は、複数使うと見出しが重なるため、`subgraph IN[入力]` のように、英数字の ID と角括弧の見出しを付ける。**書く前に、`references/mermaid-notes.md` を読み、書いた後に、記述が、そこの条件に該当しないかを確認する**。見本は、`references/exhibit-examples.md` にある。報告・説明の本文では、`<pre class="mermaid">` に書く(`references/report-and-save.md`)
- `table` と `svg`: スクリプト要素、イベント属性、`javascript:`、外部への参照を含めない
- `mock`: 動作を持たない見た目だけの HTML。スクリプトと外部通信は、隔離されて実行されない
- 画面の話は、必ず `mock` で見せる(文字だけで説明しない)
- 図表を付けない場合は、`noExhibitReason` に、理由を書く(例: 選択肢の違いが文章だけで足りるため)。図表を付けた場合は、`noExhibitReason` を書かない(矛盾するため、検証で拒否される)
- 票に、ID、パスワード、API Key、`.env` の内容などの機密情報を入れない(題名と、すべての項目が、検出の対象)

### よくある失敗(こう書かない)

- 「1. 現状」で、前提の説明なしに、いきなり「どうしますか」と聞く
- 「決めること」で、思いつきの提案を、重要なことのように書く(重要度と根拠を示す)
- 「現状」に、決定済みの事項と反映先を書かず、利用者に、理解し直させる
- 文章にする章で、「内容は〜。意義は〜。」のように、項目名を読み上げる(要素を、つなげただけにする)
- 「推奨」で、修正イメージ(何をどう変えるか)を、具体的に書かない
- 通常の文書や設定の変更に、「戻せない可能性：」を付ける(本当に戻せないときだけ書く)
- 推奨を示せないのに、根拠の薄い推奨を書く(`recommendation.none` で、示せない理由を書く)
- 画面や構造の話を、文字だけで説明する

### モックの作り方

- 外部フォント、外部画像、CDN を使わない。システムフォントと `data:` の画像だけを使う
- 動作(ホバー、切り替えなど、スクリプトが要るもの)を持たせない。CSS だけで実現できる範囲にする
- 大きさは、1 項目あたり数 KB〜数十 KB を目安にする(約 300 KB まで表示できることは確認済み)

## 手順

### 1. 検証

```bash
node "${CLAUDE_SKILL_DIR}/scripts/validate-input.mjs" <作業フォルダ>/questions.json
```

- 合格(終了コード 0)なら次へ進む。合格の行のあとに **警告** が出ることがある(`警告 N 件(票は、表示できます。…)`。mermaid の記述が、図にできないとき)。警告は、拒否ではなく、表示できる。警告が出たら、示された場所の記述を、`references/mermaid-notes.md` の条件と照らして直し、もう一度、検証する。直せない、または、直さないと決めたときは、そのまま進めてよい(表示では、図の代わりに、原文が展開される)
- 規則違反(終了コード 1)なら、画面に出さない。示された項目を直して作り直す。「古い形式」と示された場合は、新しい書式(`kind` と `items`)に書き直す
- 機密情報の検出(終了コード 1。「機密情報らしい文字列を検出」と示された欄)なら、本エージェントが、その欄から機密情報を取り除いて票を作り直し、「機密情報らしい文字列を取り除いて、票を作り直した」旨をチャットに 1 行伝える。**作り直しは 3 回まで**。3 回作り直しても検出される場合は、質問を止めて利用者に伝える。従来の質問には切り替えない
- 読み込みの失敗(終了コード 2)は、ファイルの場所と JSON の形を確認する

### 2. ローダーの生成

```bash
node "${CLAUDE_SKILL_DIR}/scripts/build-pages.mjs" <作業フォルダ>/questions.json <作業フォルダ>
```

成功すると、`admin-loader.js` の絶対パスが 1 行で出力される。

### 3. 表示

1. `new_page` で `about:blank` を、`isolatedContext: "askui"` で開く(管理用ページを別の窓にし、閉じたときに窓ごと消すため。ブラウザが最初から開いている空の窓は、閉じられずに残る)。返り値のページ番号を控える(ページ番号は固定せず、毎回 `new_page` の返り値から取得する。ブラウザの再接続で変わることがある)
2. `evaluate_script` で、そのページ番号を指定し、`sourcePath` に `admin-loader.js` の**絶対パス**を渡す。`sourcePath` は MCP サーバー側の作業ディレクトリを基準に解決される可能性があるため、相対パスにしない。**`format` は指定しない**(既定の `function` のままにする)。`admin-loader.js` は `() => {...}` という関数の形のため、`format: "script"` を付けると、関数が定義されるだけで実行されない。この失敗はエラーにならず、`undefined` が返り、`ASKUI_OPENFAIL` も出ないまま、次の待機が時間切れまで続く
3. 質問用の窓が開き、フォームが表示される。管理用ページ(手順 1 で開いたページ)は、回答の目印が出るまで閉じない
4. 窓が開いたことを確認する。手順 2 の結果に `Opened pages` として「ask-ui 質問」のページが出ていれば、開いている。出ていない場合は、待機に進まず、`format` を指定していないかと、ローダーの絶対パスを確認し、同じ呼び出しをやり直す。管理用ページが空のまま(`about:blank` で中身がない)なら、ローダーが実行されていない

### 4. 待機

`wait_for` を、管理用ページのページ番号で、次の条件で呼ぶ。

- `text`: `["ASKUI_DONE", "ASKUI_CLOSED", "ASKUI_OPENFAIL"]`
- `timeout`: `300000`(ミリ秒。1 回の待機は 300 秒)

時間切れ(目印が出ていない)の場合は、まず `list_pages` で、管理用ページのページ番号が残っているかを確認する。

- 残っている: **同じ呼び出しを繰り返す**。待機の総時間に上限は設けない。利用者が数時間後に答えても、そのまま受け取る
- 残っていない(ブラウザ全体や管理用ページが閉じられた): 繰り返さず、下の「中断」として扱う。実測では、ブラウザ全体を閉じても `wait_for` はすぐには失敗せず、時間切れまで待機が続く。その後、MCP が新しいブラウザを起動し直すため、元のページ番号は一覧から消える

注意:

- 120 秒を超える呼び出しは、バックグラウンドに移り、結果は通知で返る。質問のときは、結果が返るまで、ほかの作業を進めずに待つ(報告・説明のときは、待機を続けたまま、利用者の続きの質問に答えてよい)
- 待機中の別のブラウザ操作は、順番待ちになる。待機の途中で、同じブラウザへほかの操作を差し込まない

### 5. 結果の取り出し

目印ごとに、次のように扱う。

| 目印 | 意味 | 扱い |
| --- | --- | --- |
| `ASKUI_DONE` | 回答の送信(報告・説明では、「閉じる」または窓の × による閉鎖) | `evaluate_script` で `document.getElementById('askui-result').textContent` を取り出し、JSON として読む。`status` は `answered`。`answers` に、問ごとの `questionId`、`selected`(選んだ選択肢の `id`)、`freeText` がある。二重に送信されても、最初の 1 件だけが入っている。`save`(「この質問を保存する」の状態。なければ偽)が真なら、削除の前に保存する(下の「保存」)。報告・説明では、`status` は `reported` で、`save` と `closedBy` が入る(下の「報告・説明の手順」) |
| `ASKUI_CLOSED` | 質問用の窓の閉鎖 | 中断。下の「中断」を参照 |
| `ASKUI_OPENFAIL` | 窓を開けなかった | 表示前の失敗。下の「失敗時の切り替え」を参照 |

### 6. 後片付け(回答後、または質問用の窓の閉鎖後)

1. `close_page` で、管理用ページを閉じる。回答の取り出し(`ASKUI_DONE`)の後も、質問用の窓が閉じられた(`ASKUI_CLOSED`)後も、同じ。質問用の窓は、回答の受け取りで自動的に閉じる。残っている場合は `list_pages` で探して閉じる
2. 回答が `save:true` のときは、 **削除の前に** 保存する(下の「保存」)
3. 作業フォルダ `<作業フォルダ>` を削除する

## 中断(窓の閉鎖、接続の失敗)

次の場合は、質問を「中断」として扱う。

- `ASKUI_CLOSED` が出た(質問用の窓が閉じられた。通常 1〜2 秒、遅くとも 3 秒以内に検知される)
- 回答待ちの途中で、`wait_for` や `evaluate_script` が、ブラウザ全体の閉鎖や接続の失敗で失敗した(管理用ページが閉じられた場合も含む)
- `wait_for` の時間切れの後、`list_pages` に管理用ページのページ番号がない(ブラウザ全体や、管理用ページだけの閉鎖は、この形で現れる。管理用ページだけが閉じられ、質問用の窓が残っている場合は、その窓も閉じる。検知は、`wait_for` の 1 回分の待機時間(最大 300 秒)までかかる場合がある)

手順:

1. 「窓が閉じられたため、質問を中断した」旨を、チャットに伝える
2. 作業を止めて、利用者の次の発言を待つ
3. 途中までの回答は捨てる(一部の回答も使わない)
4. 作業フォルダを削除し、残っているページがあれば閉じる

**従来の質問(`AskUserQuestion`)に自動で切り替えない**。

## 失敗時の切り替え(表示前の失敗)

質問を表示する**前**の技術的な失敗では、黙らず、失敗を伝えたうえで、同じ質問を `AskUserQuestion` で出す。

対象の失敗:

- `new_page` が失敗した
- `ASKUI_OPENFAIL` が出た(ポップアップがブロックされたなど)
- 表示前の接続の失敗(`evaluate_script` が表示前に失敗した、など)

手順:

1. 失敗した内容を、チャットに伝える
2. 同じ質問を、`AskUserQuestion` で出す。1〜4 問の票は、分割せずに、同じ問数のまま 1 回の呼び出しで渡す(`AskUserQuestion` の 1 回の上限は 1〜4 問)
3. 質問の規則(背景、出所、意図、各選択肢の理由・メリット・デメリット、推奨を先頭、自由記入の余地)は、`AskUserQuestion` でも守る

回答待ちの**途中**の失敗は、切り替えず、上の「中断」として扱う。

## 報告・説明の手順

調査の報告や、UI を使った説明は、文章で長く書かず、同じ仕組みの画面に表示する。回答は求めない。入力は `title` と `body`(HTML。表、図、モックを置ける)の 2 項目だけ。詳細は `references/report-and-save.md` を参照する。

1. 作業フォルダ `<作業フォルダ>` を作り(下の「作業フォルダの決め方」)、`report.json`(`{"title": "...", "body": "<h2>...</h2>..."}`)を書く。題名と、タグを含まない文章だけ、必要なら推敲する(タグを含む本文は推敲を飛ばす)
2. 検証: `node "${CLAUDE_SKILL_DIR}/scripts/validate-input.mjs" --report <作業フォルダ>/report.json`(機密情報を検出したら、取り除いて作り直す。3 回まで)。本文の `<pre class="mermaid">` が図にできないときは、合格のあとに警告が出る(拒否ではない。上の「1. 検証」と同じに扱う)
3. ローダーの生成: `node "${CLAUDE_SKILL_DIR}/scripts/build-pages.mjs" <作業フォルダ>/report.json <作業フォルダ> --kind report`(説明は `--kind explain`。保存先が分かっているときは `--save-to <表示用の文字>` を足す)
4. 表示と待機: 上の「手順」の 3 と 4 と同じ。窓の題名は「ask-ui 報告」または「ask-ui 説明」。待機はバックグラウンドで続け、その間も利用者の続きの質問に答えてよい
5. 結果の取り出し: `ASKUI_DONE` の `askui-result` は `{"status":"reported","save":<真偽値>,"closedBy":"button"|"window"}`。窓の × で閉じても `ASKUI_DONE`(`closedBy:"window"`)になり、`ASKUI_CLOSED` は出ない。ブラウザ全体の閉鎖は、保存せず、その旨をチャットで伝え、作業は止めない
6. `save` が真なら保存する(下の「保存」)。そのあと、後片付け(上の「後片付け」)を行う
7. `ASKUI_OPENFAIL` のときは、`AskUserQuestion` へ切り替えない。失敗を伝え、本文を文章で要約して渡す

## 保存

保存は、利用者が指示したときだけ行う。画面のチェック(報告は既定でチェックあり、説明と質問は既定でチェックなし)か、チャットの指示で行う。`scripts/save-html.mjs` を使い、保存先と名前の規則は、プロジェクトの規則か利用者の指示に従う(なければ保存先だけを ask-ui で聞く。同じ会話で一度決まったら聞き直さない)。詳細は `references/report-and-save.md` を参照する。

- 保存は、作業フォルダの削除の **前** に行う。`--work-dir` を付けると、保存済みの確認(`saved.txt`)ができ、二度目の保存を防げる(終了コード 4)
- 質問は、`answered` かつ `save:true` のときだけ保存する。窓の閉鎖(`ASKUI_CLOSED`)では保存しない
- 「保存して」とチャットで頼まれたら、確認を挟まず、その場で保存する(窓を閉じなくてよい)。質問が回答待ちなら、未回答の質問票を保存し、回答が来たら `--update` で同じファイルに回答を加える
- 失敗(終了コード 1、2)は、チャットで伝えて、作業は止めない
- 待機中に保存先が未定のときは、ask-ui ではなく `AskUserQuestion` で保存先だけを聞く(待機中はブラウザ操作が順番待ちになり、`TaskStop` でも解放されないため)。待機は続けたままでよい

## 推敲

実行時の質問文は、日本語の推敲スキル `yomiyasu:yomiyasu` で整える。このスキルは、名前を出して頼んだときだけ動くため、**名前を出して呼ぶ**。

- 意味を変えない。許可・能力・保証の言い方(「してもよい」「できる」「必ず」「MUST」などを含む文は特に注意する)、数値、固有名詞を、そのまま保つ
- 原文と最終稿を、それぞれテキストファイルにして、検査する

```bash
node "${CLAUDE_SKILL_DIR}/scripts/polish.mjs" <作業フォルダ>/source.txt <作業フォルダ>/final.txt
```

- 終了コード 0: 検査と、最終稿のハッシュの照合が成功した。検査の記録は、スクリプトが、原文のファイルと同じフォルダ(作業フォルダ)に作り、終了時に必ず削除する(リポジトリ直下に `.yomiyasu/` を作らない)
- 終了コード 1: 検査の結果が失敗条件に当たった(意味が変わる恐れなど)。差分を確認し、最終稿を直す
- 終了コード 3: 推敲を実行できなかった(スキルが動かない、Python がない、環境の制限で止まるなど)。**推敲を飛ばして原文のまま表示**し、失敗したことをチャットで伝える。質問は止めない

### C ドライブの制限で止まった場合

推敲スキルは、利用者のホームフォルダ(`%USERPROFILE%\.claude\plugins\cache\yomiyasu\`)の下のスクリプトを読んで実行する。プロジェクトの設定で、C ドライブへのアクセスが禁止されていて止まった場合は、次の手順を取る。

1. 推敲を飛ばして、原文のまま表示する(質問は止めない)
2. 利用者に、そのプロジェクトの設定ファイル(`CLAUDE.md` など、操作範囲を定めているファイル)への例外の追記を依頼する
3. 次の文例を示す。**書き込み、削除、ほかの場所への拡張は許可しない**ことを、文例に含める

```text
例外: yomiyasu スキル(日本語の推敲)の実行に限り、`%USERPROFILE%\.claude\plugins\cache\yomiyasu\` 配下の読み取りと、そこにあるスクリプトの実行(Python 本体の利用を含む)を許可する。書き込み、削除、ほかの場所への拡張は許可しない。
```
